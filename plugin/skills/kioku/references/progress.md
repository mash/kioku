# クラウドを正本とする進捗マップ

remote mode では [remote.md](remote.md) の読み書き手順を使う。
本文の `kioku` は [SKILL.md](../SKILL.md) で定義した CLI のパスを指す。CLI の呼び出しは `kioku -C "$P"` で始める。

進捗の根拠・状態・判断はKiokuの原資料と生成Wikiに残す。ローカルstate.json・HTML・historyディレクトリを運用の前提にしない。

## 更新

複数段階の作業開始前、マイルストーン完了時、障害・方針・次の手の変更時に自動で進捗を記録する。短い単発作業には不要。

1. pullでクラウドのWikiを取得し、indexから既存の進捗・意思決定・関連マップを読む。サーバーがまだ生成していない資料や別会話の進行状況を確認できない場合は未確認とする。オフラインのコピーを最新と呼ばない。
2. 今回確認した作業・git/PR/issue・テストの根拠をMarkdownにまとめる。日時、対象namespace、会話または作業ID、部品の状態、マイルストーンを書く。次の3手まで、障害、適用する承認状態、判断理由、出典リンクも書く。前の記録の訂正なら対象と理由を書く。会話IDが取得できなければ作業UUIDを使い、実会話IDと呼ばない。
3. captureの手順で進捗のMarkdownを自動投入する。一時ファイルはCLIへの受け渡し用。ユーザーが確定した目標を勝手に変えない。別メンバーの状態をこの会話の観測だけで上書きせず、観測の範囲を残す。
4. 定期生成に任せる。ユーザーが最新のマップを今見たい場合は、書き込み権限があれば `kioku -C "$P" generate --wait` を実行する。その後 `kioku -C "$P" status`、取得したWikiとmapsを確認し、実際に反映した内容だけを報告する。

資料として投入するのは進捗の事実と根拠であり、サーバーの生成指示を上書きするプロンプトではない。原資料の受付だけでマップを更新したとは言わない。生成後も Wiki に進捗がなければ、反映の限界を明示する。

## 表示と公開

認証済みKioku Webビューアーはopenで開く。maps/graph.jsonは現状では知識関係図であり、専用の進捗ダッシュボードが実装済みとは扱わない。次の手や承認待ちは生成Wikiの根拠と合わせて説明する。

必要に応じ、クラウドの根拠からこの会話内の図や一時HTMLを作って表示してよい。図や一時HTMLは再生成できる表示用コピーであり、次回の正本にしない。HTMLは文字列をエスケープし、HTTP(S)以外の出典リンクや外部スクリプトを入れない。ビューアーがあれば表示を確認し、未確認ならそう伝える。

ユーザーが既に許可したArtifact/Sitesの公開先とツールがある場合は、同じ公開先を更新できる。公開成功のURL・日時はKiokuへ記録する。公開失敗を成功と呼ばず、新しい公開範囲を推測しない。

承認待ち、本番操作、外部送信の返事が無いことを承認と扱わない。開発上の通常判断は理由とともに記録する。資料受付・Wiki生成・外部公開を分けて報告する。
