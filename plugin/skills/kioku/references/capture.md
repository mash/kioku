# 参照・作成文書の自動記録

remote mode では [remote.md](remote.md) の読み書き手順を使う。
本文の `kioku` は [SKILL.md](../SKILL.md) で定義した CLI のパスを指す。CLI の呼び出しは `kioku -C "$P"` で始める。

Kiokuのクラウドを記録の正本にする。

重要文書を実際に参照・作成した時、結論を変えた時に、選択したプロジェクトへ自動投入する。ユーザーが通常のチーム作業として共有を許可した範囲で行い、機密・別チームの資料・保存禁止は除く。共有先が曖昧なら投入せず確認する。既存のauto_put:falseなど本人が指定した自動送信禁止は引き続き尊重するが、新しいauto_put設定は前提にしない。

## 投入

1. 日時（タイムゾーン付き）、イベントID、対象server/namespace、操作（参照・作成・結論更新）、タイトル、出典URL、版、何をしたか、取得結果を短いMarkdownにする。CLIへ渡すための一時ファイルを使い、永続ローカル台帳は作らない。
2. `kioku -C "$P" put --wait "$RECORD"` で記録のファイルだけを投入する。`RECORD` は絶対パスとする。引数なしのputで他のinboxを送らない。未確定の対象へ送らない。対象変更後も既に送信した記録の所属は変えない。
3. 原文も必要なら、ローカル原本を `kioku -C "$P" put --wait FILE` で別途投入する。agent 認証では URL の投入・再取得はできないため、正規のコネクター/API で、取得許可のある原文をファイルとして渡す。人の認証の場合だけ `kioku -C "$P" put --wait URL` も使える。記録にURLやパスを書いただけでは原文を取り込めない。
4. 受付結果とjob IDを会話で追跡する。記録の受付と原文の受付は別。jobの確認には `kioku -C "$P" job status ID`、全体の鮮度には `kioku -C "$P" status` を使う。次の会話はクラウドの記録とWikiを参照し、端末固有の処理済み位置には依存しない。

同じ会話で同じ文書・版・操作を二重投入しない。別会話で既にクラウドに記録があると確認できる場合も省く。確認できない重複を排除済みと断定しない。字句修正、日常のコマンド出力、生成Wikiの再読は記録しない。

URL取得失敗時は、正規のコネクター/APIで実際に取得できた原文があれば、出典・取得日時を付けて投入できる。本文が無ければ失敗理由のメタデータだけを記録し、未取得と明示する。タイトルから要約を作ったり、ログイン画面を原文と扱ったりしない。認証情報・署名URLの秘密部分は保存しない。

## 失敗と鮮度

読み取り専用なら送信しない。権限不足・オフラインでは「クラウド未保存」と報告し、ローカルへの保存で成功扱いにしない。復旧に必要な送信途中の一時ファイルは保持して場所を報告できるが、通常運用のローカル正本や永続キューにはしない。受付成功後は既存の安全な一時ファイル整理方針に従う。

受付成否が不明なら盲目的に再送せず、既知のjob IDを調べる。IDも無ければ未確認と報告する。失敗を確認したjobのretryは1回まで。受付と生成は別で、put --waitはWikiを更新しない。定期生成を待つか、即時反映の依頼時に `kioku -C "$P" generate --wait` を使う。
