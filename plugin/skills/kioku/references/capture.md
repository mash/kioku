# 原資料の投入

## 共通の取得規則

ユーザー自身の Claude セッションが原資料を読み、本文を Kioku に送る。
資料の種類を問わず、使えるコネクター、CLI、手元のファイル、ユーザーが貼った本文を使う。
サーバーは原資料を取得しない。

1. 原文の全文を読み、Markdown にする。要約せず、見出し・箇条書き・表・コードを保つ。
   検索結果やプレビューの抜粋で止めず、続きのページと子要素を最後まで読む。
   資料の一部をなす添付も、読める手段で本文を読む。無関係なリンク先まで巡回しない。
2. 会話やコメント、レビューは全メッセージを時刻順に並べ、各作成者と時刻を付ける。
   ツールが本文を省略した場合は、続きの取得や別の読み取り手段で補う。
   全文を読めなければ put せず、読めない範囲と未保存を伝える。
3. YAML（構造化データの記法）の frontmatter に、次の値を書く。
   `source_url` は原本の HTTPS URL、`title` は資料の題名、`fetched_at` は取得日時とする。
   版（コミット識別子や最終更新日時）があれば `version` に書く。
   版がなければ `fetched_at` と同じ日時を書く。
   日時にはタイムゾーンを付ける。本文にも題名を見出しとして含める。
4. ファイル名の拡張子を `.md` にし、文字コードは UTF-8 を使う。
   `source_url` がなければ put せず、未保存と伝える。手元のファイルやユーザーが貼った本文も同じ。
   URL を捏造せず、URL を得るためだけに原本を公開しない。

```markdown
---
source_url: "https://example.com/docs/design"
title: "設計資料"
fetched_at: "2026-11-08T10:00:00+09:00"
version: "2026-11-07T18:00:00+09:00"
---
# 設計資料

原文の全文
```

サーバーは `source_url` を必須とし、同じ資料の置き換えと削除の鍵に使う。
`source_url` は送信者の申告である。サーバーは本文と原本の一致を検証しない。

## put の前の確認

どの資料でも、送る内容について次を確認する。満たせなければ put せず、未保存と伝える。

- 本文が空でなく、ログイン画面、404、権限エラーの画面でない。
  題名やエラーメッセージだけを本文と扱わない。
- frontmatter の必須値を揃え、本文に `title` と同じ題名を含める。
- 要求全体を JSON（データ交換形式）にして、UTF-8 のバイト数を確認する。
  要求全体を 1 MiB（1,048,576 バイト）未満にする。
  CLI は `{"file":{"name":...,"content":...,"source_url":...}}` の JSON を計測する。
  MCP は `source_put` の全引数と呼び出しの構造を含めて計測する。
  frontmatter、ファイル名、JSON のエスケープも数える。CLI は `<`・`>`・`&` もエスケープする。
  上限以上なら本文の末尾を切り詰め、frontmatter の直後に切り詰めた範囲と理由を書く。
  題名と原文の構造を保ち、注記を含む要求全体を再計測する。分割して同じ URL に送らない。
  計測できない場合は要求の構造とエスケープを含む上限を見積もる。
  1 MiB 未満と確認できなければ送らない。

## ソースごとの例

次の例は一覧ではない。例にない資料も共通の取得規則に従う。

- **GitHub のファイル**: commit SHA（コミット識別子）を確定し、同じ版の原文を読む。
  `source_url` は SHA を含むファイルの `blob` URL、`version` は SHA とする。
  例: `gh api 'repos/O/R/contents/PATH?ref=SHA' -H 'Accept: application/vnd.github.raw+json'`。
- **GitHub の Issue**: 題名、本文、全コメントを含める。
  例: `gh issue view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments`。
- **GitHub の Pull Request（PR）**: 題名、本文、全コメント、全レビューを含める。
  変更ファイルの一覧と行コメントも含める。行コメントにはファイル名と行を付け、diff は送らない。
  例: `gh pr view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments,reviews,files`。
  行コメントは `gh api --paginate repos/O/R/pulls/N/comments` で読む。
  行が古い場合は元の行を使い、元の版に対するコメントと明記する。
  Issue と PR は件数を確認し、省略されたコメント・レビュー・ファイルをページ送りで補う。
- **Google Docs**: コネクターで全タブと入れ子のタブを読み、タブ名と本文を保つ。
- **Slack**: コネクターでスレッドの親メッセージと全返信を読む。
  返信のリンクを渡された場合も親スレッドを読み、スレッドの恒久リンクを `source_url` にする。
- **Notion**: コネクターでページの子ブロックを再帰的に読む。
  `version` はページの最終更新日時とする。
- **公開 Web**: ページ本文を読み、ナビゲーションと広告を除く。
  Claude Code では `curl -fsSL -- 'https://example.com/page'` などで原文を取得する。
  WebFetch はモデルの要約を返すため、Claude Code では使わない。
  claude.ai では取得ツールが全文を返したか確認し、要約や抜粋だけなら送らない。

## 共有範囲と送信

重要文書を参照・作成した時、結論を変えた文書を確定した時に、選択したプロジェクトへ送る。
ユーザーが共有を許可した範囲で行い、機密・別チームの資料・保存禁止を除く。
共有先が曖昧なら送らず確認する。`auto_put:false` などの自動送信禁止を守る。
操作の要約、イベント ID、参照した記録、取得失敗の記録を別の資料として送らない。
認証情報や署名 URL の秘密部分を保存しない。
同じ会話で同じ文書の同じ版を二重に送らない。
字句修正、日常のコマンド出力、生成 Wiki の再読は送信の対象にしない。

remote mode は、共通規則で本文を準備してから [remote.md](remote.md) で送る。
local mode は、準備した本文をファイルに書き、`kioku -C "$P" put "$FILE"` で送る。
`kioku` は [SKILL.md](../SKILL.md) の CLI のパス、`FILE` は `.md` ファイルの絶対パスを指す。
引数なしの put で無関係な inbox を送らない。一時ファイルを永続ローカル台帳にしない。
応答の inbox ID と `status: fetched` を確認し、受付結果を伝える。
複数ファイルは CLI が1件ずつ送る。途中で失敗した場合は、受付済みと未保存を分けて伝える。

資料を取り除く依頼には `kioku -C "$P" delete URL` を使う。
サーバーが `removed` の項目を受け付けた後、次の生成で source ページと参照を除く。

## 失敗と鮮度

読み取り専用なら put／delete を実行しない。
原文を読めない場合は、原本の HTTPS URL と全文をファイルなどで渡すようユーザーに頼む。
権限不足・オフラインでは未保存と伝え、別アカウントや別プロジェクトに切り替えない。
受付成否が不明なら再送せず、local mode では `kioku -C "$P" status` の inbox を確認する。
項目がないだけでは、未受付と生成済みを区別できない。判別できなければ受付不明と伝える。

サーバーは送信後の原本の変更を取り直さない。更新する時は Claude が全文を読み直して送る。
同じ `source_url` への put は、生成が使う前の項目を置き換える。
生成が使用中の項目は残り、新しい項目を次の生成が使う。
サーバーは版を比較せず、後に受け付けた本文を使う。古い版を後から送ると新しい版を上書きする。

put は受付で返り、Wiki の生成を待たない。
Wiki は定期生成か、即時反映の依頼時の `kioku -C "$P" generate --wait` で更新する。
`generate --wait` は生成完了後に pull する。受付だけで Wiki を更新したとは伝えない。
