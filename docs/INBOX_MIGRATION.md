# inbox 方式への移行

1. **運用者本人から、対象環境の旧プロジェクトデータを削除する承認を得る。** 対象の DATA、保存先、プロジェクトと削除範囲を示す。コード変更の承認は、本番データ削除の承認を兼ねない。この手順書だけを根拠に実行しない。
2. 旧サーバーで新規投入・生成を止め、実行中の session／vault の停止と片付けを完了する。`--generate-every 0` は定期生成だけを止めるので、手動生成と API への入口も止める。必要な設定バックアップ、暗号鍵、オブジェクトの独立バックアップを保管する。設定だけのバックアップから本文は戻せない。
3. kiokud を停止し、同じ保存先へ書ける旧インスタンスをすべて停止・隔離する。プロセスロックは同じホストだけを保護する。移行中に旧版を起動しない。
4. 新しいバイナリで、既存環境と同じ DATA・ストレージ設定を指定して移行する。下は手順の例であり、自動実行しない。

   ```sh
   kiokud --data /var/lib/kioku --storage local \
     --migrate-inbox --confirm-delete-project-content
   ```

   S3 なら `--storage s3` と既存の S3 接続設定を使う。設定値を変更して別の保存先を指さない。確認フラグがなければ削除しない。稼働中のサーバーがロックを保持していれば失敗する。
5. 移行の終了コードと対象件数を確認する。失敗した場合は新旧どちらのサーバーも起動せず、原因を直して同じコマンドを再実行する。プロジェクトごとに削除後に schema 2 を書くため、途中停止から再開できる。移行済みの schema 2 は再削除しない。
6. PR-2〜PR-6 を含む同じリリースの kiokud・CLI・plugin を配布し、新しい kiokud を起動する。最低 CLI バージョンは0.1.0。旧 CLI は426で拒否する。先行配布する PR-1 の CLI は版ヘッダーと `project` コマンドを備える必要がある。
7. `/healthz`、人のログイン、プロジェクト一覧、空の inbox、生成 Runner とネットワーク設定を確認する。アカウント・メンバー・接続が残り、旧本文・旧ジョブを読めないことを確認する。GitHub App の接続機能は未実装なので、公開 GitHub の認証なし取得だけを確認する。
8. 利用者へ URL／本文の put し直しを依頼する。原資料を復元してから生成する。ローカルの receipt によってファイルが再送されない場合は、既存の資料を保管したまま新しい作業ディレクトリで対象を pull し、ファイルを明示して put する。認証ファイルや元の資料を削除しない。
9. まず少量で生成・公開・pull と `wiki/log.md` を確認する。問題があれば定期生成を止め、失敗ジョブと片付け状態を調べる。旧バイナリへの切り替えでは削除済みデータは復元しない。

## 削除と保持

削除するのは content schema 1 の `wiki/`（旧 `wiki/inbox/` も含む）、`maps/`、`sources/`、ジョブの記録・入力／出力 tar、一時 inbox、content transaction と生成状態。旧ジョブの資格情報も無効にする。

アカウント、ログイン、保存済み接続、組織、プロジェクト設定、メンバー、監査記録は保持する。旧 SQLite／metadata.json の自動変換は行わない。このコマンドは現在の catalog schema 2 と旧 content schema 1 の組み合わせを対象にする。独立バックアップやオブジェクトストアの旧バージョン、利用者が取得したコピーは削除しない。

## 検証範囲

移行の削除・再開・再実行・ロック・設定保持は一時データと fake ストレージでテストする。本番データに対する移行、配布、実 Google／GitHub／managed-agent API の確認は、この実装作業では行っていない。実環境の操作は上記の承認と運用手順で別途行う。
