# 原資料の送信

## 共通の取得規則

ユーザー自身の Claude が、コネクターや CLI（コマンドラインの操作ツール）で原文を読む。
手元のファイルやユーザーが貼った本文も使える。サーバーは原資料を取得しない。

1. 原文の全文を読み、Markdown にする。要約せず、見出し・箇条書き・表・コードを保つ。
   検索結果やプレビューで止めず、続きのページと子要素を最後まで読む。
   資料の一部をなす添付も取得する。リンクだけでは本文の取得と扱わない。
   無関係なリンク先まで巡回しない。
   ページ・シート・画像・添付を列挙し、抽出結果の件数と範囲を照合する。
   会話・コメント・レビューは全件を時刻順に並べ、作成者と時刻を付ける。
2. 題名や frontmatter を追加する前に、原文自身の題名と本文で資料の実体を確認する。
   JavaScript の読み込み待ち画面、ボット確認、Cookie 同意の壁を本文と扱わない。
   ログイン画面、404、権限エラー、題名だけの画面も除く。
   HTTP（Web 通信の規約）の応答が 200 でも、本文を確認する。
   実体や全文を取得できなければ別の方法を試し、使える場合はブラウザー自動操作も試す。
   補えなければ送信せず、欠落範囲と未保存を伝える。容量による切り詰めは後述する。
3. 送信用 frontmatter（先頭のメタデータ）をファイルの最上部に1ブロックだけ置く。
   YAML（構造化データの記法）で次の4キーを各1回書く。
   `source_url` は原本の URL（資料のアドレス）、`title` は原文から確認した題名とする。
   `fetched_at` は取得日時、`version` は版の識別子か最終更新日時とする。
   版がなければ `version` に取得日時を書く。日時にはタイムゾーンを付ける。
   原文の frontmatter は本文内のコードフェンスに保ち、送信用のキーに混ぜない。
   除外・欠落・切り詰めの範囲と理由は、frontmatter 直後の本文冒頭に列挙する。
   注記の後に題名の見出しを置き、その直後に原本の時刻を箇条書きで書き、その後に原文を置く。
   欠落の注記だけで取得失敗を許容しない。
4. **原本の時刻を、原本ごとにメタデータから取って本文に書く。**
   原文に日付が書いていなくても、取得元の API や画面のメタデータから取る。
   書くのは作成日時、最終更新日時、状態が変わった日時と、その時点の状態である。
   状態の変化の例は、マージ、クローズ、公開、承認、リリース、決定である。
   例: PR は `createdAt`・`updatedAt`・`mergedAt`・`closedAt` と `state`、
   Notion は作成と最終更新の日時、Slack は各メッセージと最後の返信の時刻とする。
   最終更新日時は必ず書く。外部の Web ページのように原本に更新時刻のメタデータが無ければ、
   取得日時を最終更新日時とし、「（取得日時）」と添える。
   ほかの時刻が取れなければ、省かず「不明」と書く。日時にはタイムゾーンを付ける。
   frontmatter の `version` だけに頼らない。Wiki は本文の時刻で事実の時点と順序を決める。
5. 拡張子を `.md`、文字コードを UTF-8（Unicode の文字コード方式）にする。
   原本 URL がない場合や下記の検証に失敗した場合は、送信せず未保存と伝える。
   代わりの URL を捏造・改変せず、URL を得るためだけに原本を公開しない。

```markdown
---
source_url: "https://example.com/docs/design"
title: "設計資料"
fetched_at: "2026-11-08T10:00:00+09:00"
version: "2026-11-07T18:00:00+09:00"
---
# 設計資料

- 作成: 2026-11-01T09:00:00+09:00
- 最終更新: 2026-11-07T18:00:00+09:00
- 状態: 承認済み（2026-11-07T18:00:00+09:00）

原文の全文
```

サーバーは `source_url` を必須とし、同じ資料の置き換えと削除の鍵に使う。
`source_url` は送信者の申告である。サーバーは本文と原本の一致を検証しない。

## 送信前の確認

どの資料も次の条件を満たすか確認する。満たせなければ送信せず、未保存と伝える。

- 原本 URL は HTTPS（暗号化した HTTP）で、ホストがあり、4,096 バイト以下とする。
  ポートは省略か443とし、ユーザー情報（ユーザー名・パスワード）を含めない。
  ホストは大文字小文字と末尾のドットを正規化して検証する。
  `localhost`、`.localhost`・`.local` で終わるホストを使わない。
  IP（ネットワーク上のアドレス）を直接使う場合は、公開ユニキャストに限る。
  私用・ループバック・リンクローカル・共有・文書用などの予約アドレスを除く。
  IP バージョン4（IPv4）を埋め込んだバージョン6（IPv6）も検証する。
  原本 URL が違反する場合は別 URL に置き換えない。
- 送信本文は有効な UTF-8 とし、NUL（ゼロ文字）を含めない。
  原文の本文は空白だけではなく、題名やエラー表示以外の内容を含むことを確認する。
  YAML パーサーで送信用 frontmatter を検証する。4キーの値が揃い、重複がないことを確認する。
  `source_url` を送信引数にも指定する場合は、frontmatter と同じ値にする。
- 両モードとも、サーバーは要求を Go の `encoding/json` で再エンコードする。
  JSON（データ交換形式）の要求上限は 1 MiB（1,048,576 バイト）とする。
  安全側の計測では、`content`・`name`・`source_url` の UTF-8 バイト数を合計する。
  `content` には frontmatter と注記も含める。各値の文字に次の増分を加える。
  `<`・`>`・`&`・引用符 `"`・バックスラッシュ・U+0000〜U+001F は1文字につき5バイト加える。
  U+2028・U+2029（Unicode の行・段落区切り）は1文字につき3バイト加える。
  要求の構造用に1,024バイトを加え、合計を 900 KiB（921,600 バイト）未満にする。
  900 KiB 以上なら本文の末尾を文字・段落の境界で切り詰め、本文冒頭に範囲と理由を書く。
  題名と原文の構造を保ち、注記も含めて再計測する。同じ URL に分割して送信しない。
  計測できず、この上限未満と確認できない場合は送信しない。

## ソースごとの例

例にない資料も共通の取得規則に従う。

- **GitHub のファイル**: commit SHA（コミット識別子）を確定し、同じ版の原文を読む。
  `source_url` は SHA を含むファイルの `blob` URL、`version` は SHA とする。
  例: `gh api 'repos/O/R/contents/PATH?ref=SHA' -H 'Accept: application/vnd.github.raw+json'`。
- **GitHub の Issue**: 題名、本文、全コメントを含める。
  例: `gh issue view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments`。
- **GitHub の Pull Request（PR、変更の提案）**: 題名、本文、全コメント・レビューを含める。
  例: `gh pr view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments,reviews,changedFiles`。
  変更ファイルは `gh api --paginate repos/O/R/pulls/N/files` で全ページを読む。
  ファイル一覧の件数を `changedFiles` と照合する。差が残れば欠落件数と未保存を伝える。
  行コメントは `gh api --paginate repos/O/R/pulls/N/comments` で読み、ファイル名と行を付ける。
  古い行コメントには元の行と版を付ける。変更ファイルの一覧は含め、diff は送信しない。
  Issue と PR はコメント・レビューの件数も照合し、省略分をページ送りで補う。
- **Google Docs**: コネクターで全タブと入れ子のタブを読み、タブ名と本文を保つ。
- **Slack**: スレッドの親メッセージと全返信を読む。返信リンクからも親スレッドを確認する。
  スレッドの恒久リンクを `source_url` にする。
- **Notion**: ページの子ブロックを再帰的に読み、最終更新日時を `version` にする。
  埋め込み・インラインのデータベース（`child_database`・リンクしたビュー）も読む。
  表示ビューのフィルターと並び順を守り、対象行と関連プロパティを全ページ取得する。
  タイトルだけで済ませず、対象外のデータベース全体やリレーション先を巡回しない。
  ビュー条件や行を取得できなければ、共通規則に従って補い、補えなければ未保存と伝える。
- **PDF（文書形式）・画像・添付**: 全ページ・画像・添付の一覧と抽出結果を照合する。
  画像内の読める文字も転記し、ページ番号や添付名を保つ。読めない範囲を明記する。
- **表計算**: 全シートを列挙し、関連する全シートのデータを読む。
  値・数式のどちらを採用したか明記し、両方が必要なら両方を含める。
  シート名・行列の見出しを保ち、除外シートと理由を本文冒頭に列挙する。
- **公開 Web**: ページ本文を読み、ナビゲーションと広告を除く。
  シェルを使える場合は `curl -fsSL -- 'https://example.com/page'` などで原文を取得する。
  WebFetch はモデルの要約を返すため使わない。他の取得ツールも全文か確認する。
  読み込み待ちや要約・抜粋だけなら、共通規則に従って別の方法を試す。

## 共有範囲と送信

重要文書を参照・作成した時、結論を変えた文書を確定した時に、選択したプロジェクトへ送信する。
ユーザーが共有を許可した範囲で行い、機密・別チームの資料・保存禁止を除く。
共有先が曖昧なら送信せず確認する。`auto_put:false` などの自動送信禁止を守る。
操作の要約、イベント ID（識別子）、参照・取得失敗の記録を別の資料として送信しない。
認証情報や署名 URL の秘密部分を保存しない。同じ会話で同じ文書の同じ版を二重に送信しない。
字句修正、日常のコマンド出力、生成 Wiki の再読は送信の対象にしない。

remote mode は、本文を準備してから [remote.md](remote.md) の MCP（Model Context Protocol）で送信する。
local mode は、本文をファイルに書き、`kioku -C "$P" put "$FILE"` で送信する。
`kioku` は [SKILL.md](../SKILL.md) の CLI のパス、`FILE` は `.md` ファイルの絶対パスを指す。
引数なしの put で無関係な inbox を送信しない。一時ファイルを永続ローカル台帳にしない。
応答の inbox ID と `status: fetched` を確認し、受付結果を伝える。
複数ファイルは CLI が1件ずつ送信する。途中で失敗した場合は、受付済みと未保存を分ける。

資料を取り除く依頼には `kioku -C "$P" delete URL` を使う。
サーバーは `removed` の項目を受け付け、次の生成で source ページと参照を除く。

## 失敗と鮮度

読み取り専用なら put／delete を実行しない。
原文を読めない場合は、原本の HTTPS URL と全文をファイルなどで渡すようユーザーに頼む。
権限不足・オフラインでは未保存と伝え、別アカウントや別プロジェクトに切り替えない。
受付成否が不明なら再送せず、local mode では `kioku -C "$P" status` の inbox を確認する。
項目がないだけでは、未受付と生成済みを区別できない。判別できなければ受付不明と伝える。

サーバーは原本の変更を取り直さない。更新時は Claude が全文を読み直して送信する。
同じ `source_url` への送信では、サーバーは生成に使う前の項目を置き換える。
生成中の項目は残し、新しい項目を次の生成に使う。
サーバーは版を比較せず、後から受け付けた本文を使う。古い版でも新しい版を上書きする。

put は受付結果を返し、Wiki の生成を待たない。
Wiki は定期生成か、即時生成の依頼時の `kioku -C "$P" generate --wait` で更新する。
`generate --wait` は生成完了後に pull する。受付だけで Wiki を生成したとは伝えない。
