# 原資料の送信

## Claude Code の取り込み

PostToolUse が、選択中で書き込み可能な project の queue に、対象ツールの取得元を追加する。本文は queue に書かない。対象は WebFetch、Artifact の読み取りと公開の成功、GitHub Issue/PR の閲覧、読み取り系 MCP ツール。親は手動で登録・起動しない。手元の状態は `kioku status` で確認する。今すぐ送りたい場合は次の起動契機を案内する。

Stop と SessionEnd は選択先を、SessionStart は登録済みの全 project を確認する。queued が1件以上で有効なロックがなければ capture を起動する。Stop と SessionStart は起動失敗と failed を通知し、SessionEnd は通知しない。ロックは全行の結果がそろうか30分で解除・失効する。

capture は起動時の手順に従い、一時ディレクトリ内だけで読む・書く。公開 HTTPS の `capture fetch` は同一ホストへの HTTPS 転送9回まで、20 MiB、30秒に限る。GitHub の blob から raw への取得は例外で、原本 URL は blob のままとする。認証付き資料は snapshot の範囲で許可されたコネクターから原本を読む。許可が無ければ未保存とし、許可を広げない。

各行で `accepted`（HTTP 202 確認）、`unsaved`（取得または受付の失敗）、`skipped`（資料でないか原本 HTTPS URL を特定できない）の結果を一度返す。unsaved と skipped には理由を書く。unsaved と結果なしは合計2回まで試行する。受付は `capture.log` や `claude logs <id>` の source_url で確かめる。登録・起動は受付や Wiki 生成ではない。保存禁止の扱いは [SKILL.md](../SKILL.md) に従う。

## 原本 URL の無い Markdown

local mode では `kioku -n NAMESPACE put file:///絶対パス` を使う。frontmatter は省略でき、書く場合の source_url は `kioku:local` とする。CLI は送信用の updated_at にファイルの mtime を用い、原本は変更しない。
remote mode では `source_url: kioku:local` を frontmatter に書く。MCP は受信時刻を updated_at に使う。手順は [remote.md](remote.md) を参照する。
受け取ったローカルキーの全文を利用者に示す。本文を変えて送ると別のキーになる。古い資料は元のキーで削除する。

## 共通の取得規則

ユーザー自身の Claude が、コネクターや CLI（コマンドラインの操作ツール）で原文を読む。
手元のファイルやユーザーが貼った本文も使える。サーバーは原資料を取得しない。

1. 原文の全文を読み、Markdown にする。要約せず、見出し・箇条書き・表・コードを保つ。
   検索結果やプレビューで止めず、続きのページと子要素を最後まで読む。
   資料の一部をなす添付も取得する。リンクだけでは本文の取得と扱わない。
   無関係なリンク先まで巡回しない。
   ページ・シート・画像・添付を列挙し、抽出結果の件数と範囲を照合する。
   会話・コメント・レビューは全件を時刻順に並べ、作成者と時刻を付ける。
2. 題名や frontmatter を追加する前に、原文自身の題名と本文で資料の実体を確認する。
   JavaScript の読み込み待ち画面、ボット確認、Cookie 同意の壁を本文と扱わない。
   ログイン画面、404、権限エラー、題名だけの画面も除く。
   HTTP（Web 通信の規約）の応答が 200 でも、本文を確認する。
   実体や全文を取得できなければ別の方法を試し、使える場合はブラウザー自動操作も試す。
   補えなければ送信せず、欠落範囲と未保存を伝える。容量による切り詰めは後述する。
3. 原本 URL がある資料の送信用 frontmatter（先頭のメタデータ）をファイルの最上部に1ブロックだけ置く。
   YAML（構造化データの記法）で次の5キーを各1回書く。
   `source_url` は原本の URL（資料のアドレス）、`title` は原文から確認した題名とする。
   `fetched_at` は取得日時、`version` は版の識別子か最終更新日時とする。
   `updated_at` は手順4で確認する原本の最終更新日時とする。
   版がなければ `version` に取得日時を書く。日時にはタイムゾーンを付ける。
   サーバーは `source_url` と `updated_at` を必須とする。
   原文の frontmatter は本文内のコードフェンスに保ち、送信用のキーに混ぜない。
   除外・欠落・切り詰めの範囲と理由は、frontmatter 直後の本文冒頭に列挙する。
   注記の後に題名の見出しを置き、その直後に原本の時刻を箇条書きで書き、その後に原文を置く。
   欠落の注記だけで取得失敗を許容しない。
4. **原本の時刻を、原本ごとにメタデータから取る。**
   原文に日付が書いていなくても、取得元の API や画面のメタデータから取る。
   最終更新日時は frontmatter の `updated_at` に書く。
   本文の箇条書きには作成日時、状態が変わった日時と、その時点の状態を書く。
   状態の変化の例は、マージ、クローズ、公開、承認、リリース、決定である。
   例: PR は `createdAt`・`updatedAt`・`mergedAt`・`closedAt` と `state`、
   Notion は作成と最終更新の日時、Slack は各メッセージと最後の返信の時刻とする。
   `updated_at` は必ず書く。外部の Web ページのように原本に更新時刻のメタデータが無ければ、
   取得日時を `updated_at` に書き、本文冒頭に「updated_at は取得日時」と注記する。
   値は RFC 3339（日時の標準形式）のオフセット付き日時とする。例は `+09:00` や `Z`（UTC）。
   ほかの時刻が取れなければ、省かず「不明」と書く。日時にはタイムゾーンを付ける。
   frontmatter の `version` だけに頼らない。Wiki は `updated_at` と本文の時刻で事実の時点と順序を決める。
5. 拡張子を `.md`、文字コードを UTF-8（Unicode の文字コード方式）にする。
   下記の検証に失敗した場合は、送信せず未保存と伝える。原本に公開 URL がない資料には上のローカル資料の手順を使う。
   代わりの URL を捏造・改変せず、URL を得るためだけに原本を公開しない。

```markdown
---
source_url: "https://example.com/docs/design"
title: "設計資料"
fetched_at: "2026-11-08T10:00:00+09:00"
version: "2026-11-07T18:00:00+09:00"
updated_at: "2026-11-07T18:00:00+09:00"
---
# 設計資料

- 作成: 2026-11-01T09:00:00+09:00
- 状態: 承認済み（2026-11-07T18:00:00+09:00）

原文の全文
```

同じ資料の置き換えと削除の鍵には `source_url` を使う。
原本 URL は送信者の申告である。ローカルキーはサーバーが作る。サーバーは本文と原本の一致を検証しない。

## 送信前の確認

どの資料も次の条件を満たすか確認する。満たせなければ送信せず、未保存と伝える。

- 原本 URL がある場合は HTTPS（暗号化した HTTP）で、ホストがあり、4,096 バイト以下とする。
  ユーザー情報（ユーザー名・パスワード）、タブ、改行は含めない。サインインが必要な URL でもよい。識別子としての検査と、取得の制限を区別する。
- 送信本文は有効な UTF-8 とし、NUL（ゼロ文字）を含めない。
  原文の本文は空白だけではなく、題名やエラー表示以外の内容を含むことを確認する。
  YAML パーサーで記述済みの frontmatter を検証し、重複がないことを確認する。原本 URL がある資料は5キーの値が揃っていることを確認する。
  原本 URL のある資料の `updated_at` はオフセット付きの RFC 3339 形式とする。
  ファイル送信の `source_url` と `updated_at` は frontmatter だけに書き、送信引数にしない。
  トップレベルの `source_url` 引数は削除専用とする。
- 両モードとも、サーバーは要求を Go の `encoding/json` で再エンコードする。
  JSON（データ交換形式）の要求上限は 1 MiB（1,048,576 バイト）とする。
  安全側の計測では、`content`・`name` の UTF-8 バイト数を合計する。
  `content` には frontmatter と注記も含める。各値の文字に次の増分を加える。
  `<`・`>`・`&`・引用符 `"`・バックスラッシュ・U+0000〜U+001F は1文字につき5バイト加える。
  U+2028・U+2029（Unicode の行・段落区切り）は1文字につき3バイト加える。
  要求の構造用に1,024バイトを加え、合計を 900 KiB（921,600 バイト）未満にする。
  900 KiB 以上なら本文の末尾を文字・段落の境界で切り詰め、本文冒頭に範囲と理由を書く。
  題名と原文の構造を保ち、注記も含めて再計測する。同じ URL に分割して送信しない。
  計測できず、この上限未満と確認できない場合は送信しない。

## ソースごとの例

例にない資料も共通の取得規則に従う。

- **GitHub のファイル**: capture セッションではスナップショットの `https://github.com/O/R/blob/REF/PATH` を `source_url` とし、capture プロンプトに記載されたコマンド行をそのまま実行する。CLI が対応する raw URL に変換する。
  REF が SHA なら `version` はその SHA とする。ブランチ参照なら `version` は REF とし、本文に「SHA は固定していない」と明記して保存する。SHA 未固定だけを理由に未保存にしない。
  その他の環境では commit SHA（コミット識別子）を確定して同じ版の原文を読む。`source_url` は SHA を含む `blob` URL、`version` は SHA とし、`gh api 'repos/O/R/contents/PATH?ref=SHA' -H 'Accept: application/vnd.github.raw+json'` も使える。
- **GitHub の Issue**: 題名、本文、全コメントを含める。
  例: `gh issue view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments`。
- **GitHub の Pull Request（PR、変更の提案）**: 題名、本文、全コメント・レビューを含める。
  例: `gh pr view N --repo O/R --json title,body,author,createdAt,updatedAt,url,comments,reviews,changedFiles`。
  capture セッションでは `gh pr diff N --repo O/R` で差分を読み、変更ファイルの一覧は `gh pr view N --repo O/R --json files` で確認する。
  その他の環境では変更ファイルを `gh api --paginate repos/O/R/pulls/N/files` で全ページ読む。
  ファイル一覧の件数を `changedFiles` と照合する。capture セッションで `gh pr view --json files` が上限に達して差が残る場合は、本文に欠落件数を明記して put する。その他の環境で補っても差が残れば、欠落件数と未保存を伝える。
  capture セッションでは gh api を使わない。`gh pr view` で PR 本文と会話を取得して保存し、文書に「行コメントは未取得」と明記する。
  その他の環境では行コメントを `gh api --paginate repos/O/R/pulls/N/comments` で読み、ファイル名と行を付ける。
  古い行コメントには元の行と版を付ける。変更ファイルの一覧は含め、diff は送信しない。
  Issue と PR はコメント・レビューの件数も照合する。省略分をページ送りで補うのは capture セッション以外の環境だけとする。capture セッションでは取得できなかった範囲を本文に明記する。
- **Google Docs**: コネクターで全タブと入れ子のタブを読み、タブ名と本文を保つ。
- **Slack**: スレッドの親メッセージと全返信を読む。返信リンクからも親スレッドを確認する。
  スレッドの恒久リンクを `source_url` にする。
- **Notion**: ページの子ブロックを再帰的に読み、最終更新日時を `version` と `updated_at` にする。
  埋め込み・インラインのデータベース（`child_database`・リンクしたビュー）も読む。
  表示ビューのフィルターと並び順を守り、対象行と関連プロパティを全ページ取得する。
  タイトルだけで済ませず、対象外のデータベース全体やリレーション先を巡回しない。
  ビュー条件や行を取得できなければ、共通規則に従って補い、補えなければ未保存と伝える。
- **PDF（文書形式）・画像・添付**: 全ページ・画像・添付の一覧と抽出結果を照合する。
  画像内の読める文字も転記し、ページ番号や添付名を保つ。読めない範囲を明記する。
- **表計算**: 全シートを列挙し、関連する全シートのデータを読む。
  値・数式のどちらを採用したか明記し、両方が必要なら両方を含める。
  シート名・行列の見出しを保ち、除外シートと理由を本文冒頭に列挙する。
- **公開 Web**: ページ本文を読み、ナビゲーションと広告を除く。
  capture セッションでは 文の行ごとに記載された `capture fetch` コマンドで、文の一時ディレクトリ内の新しいファイルへ原文を取得する。
  その他の環境でシェルを使える場合は `curl -fsSL -- 'https://example.com/page'` などで原文を取得する。
  WebFetch はモデルの要約を返すため使わない。他の取得ツールも全文か確認する。
  読み込み待ちや要約・抜粋だけなら、共通規則に従って別の方法を試す。

## 共有範囲と送信

Claude Code の local mode は PostToolUse の登録と [SKILL.md](../SKILL.md) のローカル Markdown・保存禁止の手順を使う。
その他の環境では、重要文書を参照・作成した時、結論を変えた文書を確定した時に送信する。
ユーザーが共有を許可した範囲で行い、機密・別チームの資料・保存禁止を除く。
共有先が曖昧なら送信せず確認する。`auto_put:false` などの自動送信禁止を守る。
操作の要約、イベント ID（識別子）、参照・取得失敗の記録を別の資料として送信しない。
認証情報や署名 URL の秘密部分を保存しない。同じ会話で同じ文書の同じ版を二重に送信しない。
字句修正、日常のコマンド出力、生成 Wiki の再読は送信の対象にしない。

remote mode は、本文を準備してから [remote.md](remote.md) の MCP（Model Context Protocol）で送信する。
Claude Code の capture セッションは文の一時ディレクトリを使い、結果がそろったら CLI が削除する。
Claude Code 以外の local mode は、`mktemp -d` を単独の Bash 呼び出しで実行して一時ディレクトリを作る。
出力した絶対パスをそのまま書き、シェル変数や `$(...)` は使わない。
そのディレクトリに原資料の Markdown を書き、`kioku -n "$NAMESPACE" put PATH` で送信する。
`kioku` は [SKILL.md](../SKILL.md) の CLI のパス、`PATH` は `.md` ファイルの絶対パスを指す。
`PATH` には実際の絶対パスをそのまま書く。受付状態を手元に記録しない。
Claude Code の local mode では、CLI が状態ファイルに会話の選択を残す。
状態ファイルの期限は最後の書き込みから30日とする。
フックが状態ファイルを書くのは trigger 語の自動選択時だけにする。
受付状態はサーバーで確認する。
コマンドの成功を確認し、Kioku がファイルを受け付けたとユーザーに伝える。
複数ファイルは CLI が1件ずつ送信する。途中で失敗した場合は、受付済みと未保存を分ける。

資料を取り除く依頼には `kioku -n "$NAMESPACE" delete SOURCE` を使う。
`SOURCE` には取得元、原本 HTTPS URL、または完全なローカルキーを指定する。受付前の tool: は queue の行だけを消す。HTTPS URL は queue の行を消して、あわせてサーバーへ削除を依頼する。
サーバーは次の生成で source ページと参照を除く。

## 失敗と鮮度

読み取り専用なら put／delete を実行しない。
原文を読めない場合は、全文と、原本 URL があれば URL も渡すようユーザーに頼む。
権限不足・オフラインでは未保存と伝え、別アカウントや別プロジェクトに切り替えない。
capture セッションでは status・version を実行しない。202 を確認できなければ理由付き unsaved とし、同じ capture セッションでは再送しない。
`put file:` で受付成否が不明なら、本文を変えずに同じコマンドを実行し直せる。`put PATH` で受付成否が不明なら自動で再送せず、 `kioku -n "$NAMESPACE" status` のサーバーの inbox を確認する。
項目がないだけでは、未受付と生成済みを区別できない。判別できなければ受付不明と伝える。

サーバーは原本の変更を取り直さない。更新時は Claude が全文を読み直して送信する。
同じ `source_url` への送信では、サーバーは生成に使う前の項目を置き換える。
生成中の項目は残し、新しい項目を次の生成に使う。
サーバーは版を比較せず、後から受け付けた本文を使う。古い版でも新しい版を上書きする。

ファイルの put は inbox に受け付け、Wiki の生成を待たない。queue の queued はまだ受付前を示す。
Wiki は最後の put の約 10 秒後の自動生成か、即時生成の依頼時の `kioku -n "$NAMESPACE" generate --wait` で更新する。
`generate --wait` は生成完了後に pull する。受付だけで Wiki を生成したとは伝えない。
